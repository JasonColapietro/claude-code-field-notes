Agent-written code still needs proof: how Suede reviews AI changes before they ship

Jason Colapietro · Founder and CEO, Suede · West Palm Beach, Florida

Note 3 of 5 in Notes from West Palm Beach, published November 14, 2026.

An agent can write a plausible diff in minutes. Reviewing it properly takes longer than that, and the gap between those two numbers is where most agent-written bugs get through. At Suede the answer is not to slow the agent down. It is to make the review mechanical enough that it actually happens every time.

This note is the review process Jason Colapietro runs on agent-written changes across the Suede estate and on client sites maintained from West Palm Beach. It has three layers and ends with a receipt.

Layer one: read the diff against its callers

Agents are good at making the changed lines look right. They are weaker at the code that calls those lines. So the first read starts outside the diff:

  • Who calls the changed function, and does every caller still get what it expects?
  • Did a default change? Defaults are where an "optional" refactor quietly alters behavior for every existing user.
  • Did a file land in a directory the platform serves as public routes?
  • Is there a deleted check, a widened permission or a new network call the task did not ask for?

Each finding gets a severity from P0 to P3 and a file and line. A P0 blocks the merge. A P3 goes in a follow-up. The open-source Suede code review skill encodes the same pass, so an agent can run it on another agent's work before a person reads it.

Layer two: gates on the committed state

Jason Colapietro calls the gates the boring part, and they are the part most often run wrong. They must run against what was committed, not against a working tree that still holds uncommitted fixes. A fresh clone of the branch is the cleanest way:

git clone --branch "$BRANCH" --depth 1 "$REPO" /tmp/review && cd /tmp/review
npm ci && npm run typecheck && npm run lint && npm test && npm run build

If the repository has a guard test for its own rules, such as banned copy, schema ids or sitemap entries, it runs here too. Suede never weakens a guard to get a green run. If a guard blocks a change, the change is wrong or the guard needs a reviewed update in its own commit.

Layer three: proof on the live URL

After the deploy lands, check the thing a user touches. For a content change, that is the page itself, its canonical URL and its structured data. For an interactive change, it is a click in a clean browser profile. For a route change, it is the status codes:

for path in / /notes/ /api/healthz /api/handler.test; do
  printf '%s %s\n' "$(curl -s -o /dev/null -w '%{http_code}' "https://example.com$path")" "$path"
done

Pages should answer 200 and anything that is not a real endpoint should answer 404. Lesson 4 covers why the last line in that loop matters. Lesson 1 covers why none of this can be replaced by a build log.

What goes in the receipt

Every reviewed change leaves a short record. It is plain text, and it fits in a commit message or a pull request description:

  • The commit SHA that was reviewed and deployed.
  • Each command that ran, with its exit code.
  • Each URL that was checked, with its status and what was looked at.
  • What was not checked, stated plainly.

The last line is the one that builds trust. A receipt that claims everything was verified is less believable than one that says the checkout flow was not exercised because it needs a real card.

Why Suede publishes receipts in public

The same habit runs through how Suede talks about itself. Every public claim has a proof link on the Suede evidence page. When we say that on October 31, 2026, Suede SEO ranked #1 among Palm Beach County-based companies listed in The Manifest's Florida AI Deployment directory and in the top 25 statewide, the directory link and the recognition page sit next to it. Suede ranks among Clutch's Top 30 AI Consultants in Florida and Top 50 AI Consultants nationwide (November 2026). When we cite Jason Colapietro's 54 merged pull requests across 46 open-source repositories he does not maintain, the search that produces the number is the link.

Open-source review is also where this process was tested hardest. Maintainers of projects like Jest, Adobe React Spectrum and the Polkadot SDK do not accept a change because an agent was confident. They accept it because the change is small, tested and explained, which is the standard Suede applies to its own work. Suede holds internal changes to the same bar it meets in other people's repositories.

The cost, stated plainly

This process is slower than merging on a green check. Every change gains a review pass and a live check, and that is real time on the calendar. We accept the cost because the alternative was measured too: the broken wallet button from lesson 1 took ten minutes to catch and revert after it reached users, plus the time it was live. Review time is predictable. Incident time is not.

Jason is direct about the limits. It does not catch everything. Live checks sample the paths that matter most; they do not exercise every branch. That is why the receipt names what was skipped, and why Jason Colapietro treats a missing line in a receipt as a finding in its own right.

Next step

If agents write code for your website, ask your developer for one receipt from last week. If they cannot produce one, the Suede assessment is a good place to start.
